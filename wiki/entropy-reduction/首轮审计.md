# 房产视频 Skill 熵减 · 首轮只读审计

关联[实施方案](方案.md)。这是本轮已读文件的静态审计快照，不是全仓检查结果，也不是运行测试回执。工程当前状态仍见[根 HANDOFF](../../HANDOFF.md)。

## 1. 结论与证据边界

**应优先修复“当前模板→生成→宿主提交→制作 CLI”的契约差异，而不是先整理目录。** 已确认有导航版本漂移和代码条件不一致；是否在某一真实生产路径实际触发，需要维护模式下用现有工具复现。

本轮实际完成：

- 宿主 `video_gate_status` 回读为 `loaded=true`、`mode=production`、`state=SCRIPT_REQUIRED`、`production_authorized=false`。
- 读取项目 README、HANDOFF、Wiki 导航、旧约束审计；沿明确路径读取当前模板、生成/校验/批准调用链和相关已有测试。
- 检查新成果目标路径未存在，创建方案与技术图源；没有修改技能、门禁或生产素材。

未完成：全目录枚举、Git 根/工作区基线、所有局部规则发现、所有调用方和测试覆盖检索、代码执行、Pi 重新加载、真实 MCP、图源渲染、PNG 导出、任何视频制作。本轮没有运行测试，也没有提交或推送。

证据分级：

- **静态已证实**：可以直接从已读取的字段或分支得出差异。
- **运行待复现**：指出明确路径和预期失败条件，但尚未执行输入。
- **范围待决**：已有规则是否适用于所有任务，需要核真实需求来源。
- **保留/未证实缺陷**：已有代码或文档消除了最初疑点，不以复杂为由删去。

优先级：P1 为关键流程/授权交接，P2 为维护与易误用问题，P3 为导航一致性。此排序不是事故概率或已发生损害的统计。

## 2. 已证实差异与最小验证计划

### ER-01 · 当前 v3 的同一 HTML 资产角色在两段检查中互斥

**P1 · 静态已证实；运行待复现；未修复。**

证据：

1. [record 模板](../../skills/vr-production-gates/assets/templates/record.json)：`视频剧本.html` 的 role 为 `storyboard_source`；`scope.storyboard_layout.source` 与 `presentation.document_path` 都指向该文件；schema 为 v3。
2. [check_shooting_plan.py](../../skills/vr-production-gates/scripts/check_shooting_plan.py)，`check` 的 v3 布局分支：`source` 对应 role 必须为 `storyboard_source`，否则 `unbound_storyboard_layout:source`。
3. [approval/snapshot.py](../../skills/vr-production-gates/scripts/approval/snapshot.py)，`snapshot`：HTML 资产接受 `integrated_review_source` **或** `storyboard_source`。
4. [document_review.py](../../skills/vr-production-gates/scripts/document_review.py)，`check_document`：linked_document 且审核文件不是 Markdown plan 时，只接受 `integrated_review_source`，否则 `unbound_review_document`。
5. 同一资产不能简单写两条 role 解决：[check_shooting_plan.py](../../skills/vr-production-gates/scripts/check_shooting_plan.py) 对重复路径报 `duplicate_asset`；宿主快照也要求对应 HTML 资产唯一。

影响条件：沿用当前模板，把同一个 HTML 同时作为方案板源和审核文档；即便其他字段齐备，review 与后续 capture/post 的角色要求仍不一致。不能声称已经观察到真实制作失败，但这组条件自身不一致。

最小验证：用已有 v3 fixture 补齐合法来源/正文/回执，在同一个文件身份下依次调用 review、snapshot、capture 检查；隔离 role 变量并记录各错误码。然后在同一现有输入模型内统一“整合 HTML”的角色约定，保持旧数据兼容和 SHA 校验，不新建第二份 HTML，也不删除宿主门禁。

验收：当前同源 HTML 可连续通过各阶段的对应结构检查；错资产、重复资产、错 SHA、隐藏内容仍被拒绝。

### ER-02 · 生成正文未自动嵌 overview，而提交检查无条件要求它

**P1 · 静态已证实；当前生成到提交的影响待整链路复现；未修复。**

证据：

- [storyboard/render.py](../../skills/vr-production-gates/scripts/storyboard/render.py)，`render_markdown`：输出 HTML 链接、章节源图、可选 design_preview PNG；没有按 role=overview 输出图片引用。
- [build_script_package.py](../../skills/vr-production-gates/scripts/build_script_package.py)，`build_package`：写 HTML、正文、generation.json；明确不导出 PNG、不输出完整 rebased record，也未向正文追加 overview 图片。
- [check_shooting_plan.py](../../skills/vr-production-gates/scripts/check_shooting_plan.py)，`check`：要求至少一个 overview 且每个 overview 的绝对解析路径出现在 Markdown 图片中，否则 `missing_embedded_overview`。
- [填写说明](../../skills/vr-production-gates/references/illustrated-script-template.md)要求截图导出 overview、绑定图片与图源，却未明确“生成后仍须补 overview 到 Markdown”这一步；同时称不再手工维护重复 Markdown 台本。

影响：只做“填 record→build→截图/刷新 SHA→submit”的字面流程可能不能闭合，执行者需要隐式补正文或依赖未核实的其他脚本。这里不把“未自动输出 rebased record”单独定成 bug；它可以是调用方责任，但责任与完整步骤必须明确。

最小验证：从当前模板/现有 v3 fixture 生成完整包，记录生成目录与输入目录间的路径绑定，截图资产齐备后提交；确认是否出现 `missing_embedded_overview`，并检查实际调用方是否已有补图逻辑。最小修复应在已有生成流程中统一嵌图/绑定，不建立第二套台本或通用打包框架。

验收：按文档列明的步骤能从当前 record 得到可提交完整包，目录相对路径正确，引用与 SHA 可核；缺 overview 或引用旧图片仍失败。

### ER-03 · 宿主与 CLI 对“真实确认”的责任和可接受用语没有闭合

**P1 · 静态差异已证实；运行待复现；未修复。**

证据：

- [approval/policy.mjs](../../skills/vr-production-gates/scripts/approval/policy.mjs)，`approves` 允许“确认本版脚本，开始制作。”等明确表达。
- [test_approval_runtime.mjs](../../skills/vr-production-gates/tests/test_approval_runtime.mjs)已有 `rpc-user-confirmation-supported` 场景采用这句话；此处只是读到测试代码，未运行它。
- [document_review.py](../../skills/vr-production-gates/scripts/document_review.py)，`check_submission` 的 `yes` 正则包含审核通过、批准、同意执行、确认执行、接受后开始/继续、approve，但没有覆盖上面的具体表达。
- [approval/index.ts](../../skills/vr-production-gates/scripts/approval/index.ts)将确认保存在 `pending.approved/userMessage`，不回写 record 或导出 CLI 转录。
- [check_shooting_plan.py](../../skills/vr-production-gates/scripts/check_shooting_plan.py) 的非 review 分支仍要求 `status=SCRIPT_APPROVED_ONCE`、转录 SHA、展示/用户事件、批准快照，随后调用 `check_document`。

影响：宿主已接受的真实确认，按原文交给旧 CLI 可能被拒绝；从宿主状态到 CLI 所需事件格式的交接也没有在已读入口实现中看到。不能靠让 Agent 改写用户原话、伪造批准或要求用户再批一次解决。全仓是否存在其他适配器尚未检索，需保留这个限制。

最小验证：固定真实用户句子并隔离其他错误，比较宿主与 linked_document CLI 的接受结果；沿实际调用方查清真实事件如何导出。选择一个可信身份权威，CLI保留必要内容/来源/范围约束与历史兼容，避免两套自然语言判定独立漂移。

验收：合法本版确认在整条链路语义一致；模糊、否定、错误版本、伪造转录、错分支不能越权；不新增第二次用户审批。

## 4. 初始疑点的反证：这些机制应保留

### 4.1 转场基准与重复乘速已有确定性保护

[showcase.py](../../skills/vr-production-gates/scripts/storyboard/showcase.py) 的 `accelerate_transitions`：只对 `content_mode=transition` 乘倍率；包含 `baseline_speed_map` 的回执拒绝再作为基准；缺分类或无转场会失败。

[retime.py](../../skills/vr-production-gates/scripts/technical_examples/retime.py)保留 `baseline_speed_map` 与实际 `speed_map`，前后均调用完整时间线校验。[路线文档](../../skills/vr-production-gates/references/short-route-motion.md)也明确基准2倍→有效3倍。

结论：入口“原方案上×1.5”仍可更精确，但不能把它升级为已确认的二次乘速缺陷，也不能删除已有保护。未运行 FFmpeg，不声称实际媒体已验证。

### 4.2 review 与动态预检不是无条件循环依赖

[check_shooting_plan.py](../../skills/vr-production-gates/scripts/check_shooting_plan.py)只有非 review 阶段调用 `render_precheck`；门禁协议允许先提供候选脚本、待真实确认后进行所需动态预检。

结论：不能说所有候选脚本都必须先录视频才能提交；真正需澄清的是模板资产生命周期、审核页打开方式及文档顺序（ER-05）。

### 4.3 宿主与 CLI 不同层保护不应简单合并删除

宿主对真实用户来源、分支和快照负责；CLI对内容/来源/范围/输出保护及历史数据负责。两者都存在并不等于重复。需对齐接口和真值来源，而不是为了“少一层”撤销保护。

### 4.4 已有熵减历史，不应再发明评分框架

[既有约束审计](../cases/CASE-20261015-003-constraint-audit.md)已记录62类约束取舍及删除旧次数配额的理由。新审计复用它作为历史线索，不把旧评分当当前自动决策，也不新建评分数据库。

## 6. 续接顺序

1. 用户开启 `/video-gate maintenance` 后，立即用宿主状态核实，不把聊天中的文字当状态改变。
2. 查真实 Git 根和工作区、局部规则、实际加载；保留用户改动。
3. 导出技术图 PNG、回读图像、嵌入方案，并运行现有图文检查。
4. 从 ER-01～03 开始最小离线复现，检查已有全链路测试后补必要缺口。
5. 按方案实施小批量修复，更新已有问题记录；正式登记前先查同根因旧条目，不重复建问题真值。
6. 跑相关验证、复核差异、更新根交接，按项目约定检查后提交推送。

本审计不独立维护未来修复状态。后续结果应链接项目已有问题/证据记录；本页作为本次静态发现快照保留，必要勘误显式追加。
